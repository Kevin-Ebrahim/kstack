# Review perspectives

Choose perspectives grounded in the actual audience. These are prompts for a walkthrough, not claims that real people behaved this way. Do not invent research results or require all perspectives for every target.

- **Frequent experienced user:** Can common actions be repeated efficiently? Are keyboard paths discoverable? Do redundant confirmations, forced tours, or one-item-at-a-time interactions impede a genuinely repetitive task?
- **Newcomer:** Is the first useful action clear? Do labels explain domain concepts where needed? Can the person recover from an understandable mistake without losing work?
- **Person using assistive technology:** Can the primary task be completed with keyboard navigation and meaningful names? Are focus, reading order, announcements, zoom, and non-color information usable? Check with the relevant tools rather than guessing from a screenshot.
- **Person encountering adverse states:** What happens with empty, huge, malformed, translated, or delayed data; refresh; navigation backward; interrupted work; and partial failure? Does the interface accurately describe the result?
- **Person on a mobile device:** Are the target controls reachable and distinguishable, inputs suitable, and progress preserved during relevant interruptions? Check actual input behavior and performance when possible, not just viewport size.

Use product documentation to add a role these prompts miss. Walk a concrete task for each selected perspective and report only specific observed problems or clearly marked hypotheses. A control near the top of the screen, several visible options, or an absent bulk action is not automatically a defect.
